Native Ninja vertex initialization lifecycle - initial integration
Overall project estimate: about 10%; goal active; full game remains unfinished.

The SDK-facing njInitVertexBuffer entry now runs a native adaptation using the
real shared vertex queues, real original Ninja blank callback, native rational
wait clock and actual original njCalcTexture. A higher module imports the frame
and presentation modules, preserving their acyclic ownership. Its SDK globals
are committed after allocation succeeds. Percentages use value-only RZ scalar
multiply/divide and a truncating integer-to-binary32 conversion.

The Windows shared-variable declaration conflict is resolved by an operation
in the existing texture owner: jp_texture_cache_maximum updates the same actual
SDK cache variable. No duplicate cache or modified SDK header is required.
The SDK entry is an adapted implementation, not an unchanged matching body.
It uses separate real host allocations rather than a console heap alias. The
generic kmSetSystemConfiguration hardware/framebuffer lifecycle is unfinished;
the config structure's pVertexBuffer is NULL for these noncontiguous host pools.
Do not present this as a complete generic Kamui configuration implementation.
Caller-supplied console vertex-buffer semantics remain unimplemented.

Failed waits/texture checks/allocations now cancel the newly armed original
Ninja blank handler. Cleanup is allowed after terminal wait failure without
clearing that failure. A recycled slot occupied by an unrelated callback is
preserved. Busy/reentry guards protect the original wait/chain owner.

callbacks and original texture query ran; no native function was substituted.

maximum, SDK entry, invalid arguments, real allocation failure and retry,
