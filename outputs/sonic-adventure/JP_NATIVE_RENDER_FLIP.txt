Native render/flip, completion callbacks and measured statistics
==============================================================

Status: VERIFIED component milestone. Estimated whole-project completion remains
about 10% of weighted milestones, not code coverage. Goal active. Japanese
matching/GCC source baselines remain verified. English, complete native gameplay
and later platforms remain unfinished. These research builds are not playable.

What changed
------------
kmRender now captures the real packet queue into an owned frame and submits an
actual GPU job. kmFlipFrameBuffer polls real completion, dispatches the registered
EOR callback once on the game thread, waits for a future logical tick, copies the
completed GPU target to the window and calls real Present. Successful flip
retires both frame/job owners and advances the native write-slot index modulo
four. kmResetPointer drops the actual recording. No CPU image transfer occurs
in this production path. One submission may await flip; duplicate render is an
explicit sequence error. This is a serial native adapter, not a recreation of
Kamui's original four-slot DMA/2V/3V hardware latency behavior.

The typed kmiIntStatisticData is now owned by real native work. render_start
and ta_start use complemented wrapping wall counts. ta_time measures synchronous
capture/preparation/submission. render_time measures native submission through
observed completion, including preparation, queue and polling delay. It is a
native conservative estimate, not a console-only raster duration. GPU timestamps
remain separately qualified by their disjoint validity flag; CPU/GPU absolute
timestamps are never subtracted. Unused hardware DMA/overflow fields describe
no such native operations; they are not fabricated measurements.

The actual GCC pvr_fits body has a guard which refuses split-frame estimates
until a real native completion sample exists, or while the backend has failed.
The rest of its original prediction remains intact. Original frame_wait and
show_first now stop on backend failure; show_first also restores timer-1 state
before returning. Audio, bitmap, loading and other game services in the isolated
integration DLL remain explicitly labelled trace providers. Render/flip/reset,
GPU jobs, callback registration, statistics and window presentation are real.

Device ownership and failure behavior
------------------------------------
The adapter uses the SAME typed kmiDeviceExtension as SDK video setters and
frame-state capture. A private export-only relink exposes its address for
diagnostic binding; every original frame-owner object stays byte-identical.
Production jp_present_initialize_sdk binds the existing global directly.
No second device record or clock provider is created by the public library.

Initialize clock/waits/video, bind the presenter, then install frame pacing and
game EOR callbacks. Use a matching GPU/window pair. Stop/drain the presenter
before resetting video/clock/wait/frame owners. Snapshot IDs are borrowed for
inspection; the presenter owns their release. The window/GPU/context/callback
storage must remain valid until shutdown finishes.

Capture failure preserves the recording. GPU failure after capture retains the
owned frame for explicit drain. Unsupported presort/fog/background/texture
states continue to fail instead of being forced into a passing mode. Failed
present/timeout/closed-window paths do not increment native successful-Present
counts. A terminal failure stops later original frame work. Shutdown drains GPU
ownership without game callbacks even after the window/tick host closes. A drain
failure retains ownership for a later attempt, rather than forgetting work.
The original application loop must check native wait/presenter status and stop
its iteration; that full loop is not implemented yet.

Each flip chooses the next logical boundary after readiness is observed and
overdue callbacks are serviced. Controlled-clock tests verify that a second
unconditional tick is not inserted. Late host observation is conservative;
physical scanout timing is not proved. Native wall timing runs while timer 1 is
paused. Present interval 0/1 is a backend option, not a completed FPS settings UI.
