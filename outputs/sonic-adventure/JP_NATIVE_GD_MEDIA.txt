Native data-track transport and original GDFS directory software
Whole-project estimate: approximately 10%; goal active.
Status: VERIFIED COMPONENT. Complete GDFS startup/drive interface, system
bootstrap, audio, gameplay, English, enhancements, VMU Chao program/widget and
later platforms remain unfinished. Matching source completion is separate.

What changed
The original GDFS directory software now reads the user's actual Japanese
Dreamcast data track through a real native file-backed sector transport. This
keeps the original ISO9660 record parsing, directory loading and filename search
code available for the native port. It does not execute SH-4 game instructions
at runtime. The transport is authored host C; the original directory C is built
privately from the pinned external source for qualification.

The host transport opens the supplied track read-only, against concurrent
writers, with actual Windows overlapped I/O and an owned completion event.
Requests use explicit frame addresses (track LBA+150) and declared sector-count
limits. One creating game thread owns one request at a time. Cooked 2048 and
Mode1 raw 2352 data sectors are supported; raw data yields contiguous 2048-byte
payloads after validating every header. The real Japanese track demonstrates
extended minute bytes A0 and C2 beyond minute 99; these remain valid. There is
no audio-track, Mode2, ECC correction, physical seek timing or CD-DA support in
this data transport component.

Requests own both raw I/O staging and decoded output buffers. No partial raw
request becomes a visible decoded view. Invalid bounds, an unsupported sector
format or a bad later header fail the request without publishing partial data.
A view's lifetime ends at explicit release/close. Pending OS write buffers
cannot be replaced or freed. Foreign-thread mutation/close rejects without
changing ownership or caller output. Read waits and cancellation/drain waits
accept 0..60000ms; timeout retains resources for retry. Close cancels/drains first,
then releases buffers and actual file/event handles. A failed handle close
retains the remaining handle for retry rather than dropping its ownership.

Original software reused
Nine complete function bodies are compiled unchanged: name_upper, gdFsMemcpy,
name_same, name_same_any_case, name_sid, read_dirrec, gdFsGetDirEnt,
gdFsSearchName and gdFsCreateDirhn. Their serialized directory entries remain
44 bytes, with a 16-byte directory header. The upstream GCC initialization of
dr is enabled in gdFsGetDirEnt. Full original game/SDK input files remain pinned
at commit 25a3d3154dbe657325e97dbe8c5291086f6af5c0 and hash-verified.

The private qualification fixture validates record geometry/name bounds before
entering the original parser and stages a directory before returning it to a
caller. It bounds directory reads and reports actual I/O failure and original
DIROVER results. Its gdFsReadW adapter is DIRECTORY-ONLY: it validates each
sector as a directory and is not a general production GDFS replacement. Do not
install that fixture globally: PVDs, path tables and ordinary game payloads
require different validation. The production native transport accepts ordinary
sector data; future GDFS integration must retain appropriate bounds at each
original parser's own boundary.

Verification
verify_native_gd_media.py passes 8860 assertions. It exercises real cooked/raw
file I/O, multi-sector reads, ranges/overflow, stable full-width output views,
pending-buffer protection, cancellation/drain, creator-thread restrictions,
overlapping outputs, concurrent-writer exclusion and malformed raw headers.
It creates only fresh local fixture files and opens the user's disc read-only.
Zero-time read/cancel observations in the final run both completed immediately;
the timeout return branch was not observed on this fast local storage. The
code's timeout-retention behavior remains reviewed, rather than claimed as an
observed slow-I/O result. No fake OS completion or delay source was substituted.

The actual Japanese data track is 1185760800 bytes: 504150 raw 2352 sectors starting
at FAD45150. Its PVD, first/last sectors, minute99/100 boundary and random spans
match independent direct-file extraction. Full SHA256 before/after native reads:

Neither input is changed or copied into public artifacts.

The original directory loader reads all 248 root entries and 1863 SONICADV entries
from actual native sector requests (six root sectors and 45 SONICADV sectors).
Every extent, size, flag, search ID and
filename matches an independent ISO9660 reader. Exact and case-insensitive
native searches cover every entry. The original binary executes 2143 complete
calls without function hooks: 2111 original record parses and 32 full searches.
Parser fields and surrounding canaries match after pointer relocation. Directory
overflow and malformed-record tests preserve caller data. The source bodies
and original image hash remain unchanged; no original function is replaced in
that instruction oracle.

Three distinct complete game files, including the original 1ST_READ.BIN and an
actual PRS asset, are recovered through native transport and compared against
independent extraction. Native 1ST_READ.BIN is 6783232 bytes and exactly matches

This proves data retrieval, not execution of the full program or a new gameplay
