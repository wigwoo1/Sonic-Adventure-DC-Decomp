What now runs
The actual original ARM sound driver advances at44,100 sample frames per second
of counted elapsed time, through the qualified AICA core and Windows output.
It uses integer quotient/remainder accumulation, preserving fractional samples
across calls. Caller/render cadence does not determine firmware speed. The two
original driver boots occur before the new real-time anchor; their88,200 warmup
frames are not charged again as real-time playback debt.

The native message-wait function services an owned periodic callback before and
after its real Windows wait, limiting a requested sleep to the active period
(1..10ms). The existing game thread runs all SDK/ARM work; the WASAPI worker
continues to own only copied PCM delivery. No worker calls game code. There is
one wait, clock, SDK, core and sound owner. The original frame-wait/deadline and
clock bodies remain preserved. An unbound optional periodic callback does not
pretend to initialize or service audio.

Production entry: jp_system_start_sound_clock(sound_options,clock_options).
It starts the actual original game sound through the qualified compiled System
and existing exit registration, then starts the timed service. A failed clock
provider/startup rolls back sound and the borrowed core. An already-owned wait
callback is rejected before audio acquisition. Older explicit-progress entries
remain available for offline/reference clients; they are not the timed main
entry. No false-success void sound_system_init or higher main entry is added.

Clock options are56 bytes: size,quantum,max frames per tick,period, optional
borrowed source/context/frequency and an activity guard/context. NULL source/
context/frequency uses the actual shared native wall clock at781250 counts/sec.
The explicit clock provider exists for deterministic arithmetic checks, not to
replace the SDK/ARM/audio. System's timed entry supplies its real activity guard;
callers leave those two fieldsNULL. The clock snapshot is136 bytes. Quantum is
1..2048 frames; per-tick work is bounded by quantum..8192 frames. Rate is44100.

Progress, output pressure and lifetime
- Each tick accounts for all new elapsed time, then performs bounded real SDK
  servicing and firmware/PCM work. A full actual PCM queue does not advance the
  core; unrendered elapsed frames remain debt. A later tick recovers that same
  debt after the real worker frees capacity, rather than dropping samples.
- Explicit sound render/pump cannot double-advance firmware while timing owns
  it. Snapshot/service operations retain their established creator-thread rules.
- stop(0) samples newly elapsed time and rejects outstanding debt. stop(1) is an
  explicit cancellation: it records unrendered cancelled frames, never reports
  them rendered/played, and does not advance the core. Cleanup uses cancellation
  before retiring callback/context, SDK, transport, output or core memory.
- Borrowed source/activity contexts are cleared after unbind. Failed cleanup
  retains unfinished real ownership for retry. Tokens never recycle; active
  callbacks cannot recursively dispatch, replace or retire their own binding.
- System/Exit activity guards prevent an actual sound callback from beginning
  global shutdown while firmware work is live, both before and after final
  binding. The original single System bootstrap registration remains authoritative.
- Failed/backwards/overflowing clock sources stop the actual wait with its
  terminal host error. The error is not reset to make cleanup appear healthy.
  Once quiescent, still-owned vblank callbacks may be identified/removed for
  teardown; new registrations remain rejected. GDFS/RTC can therefore verify
  their exact callback identities before releasing storage after a fatal wait.
  Foreign-thread or active-dispatch retirement remains rejected. Healthy chain
  deletion/inspection still delegates to the unchanged qualified implementations.
