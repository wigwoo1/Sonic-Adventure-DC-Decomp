Actual native device behavior
Eight independently owned LCD endpoints follow enabled and actually attached
cards in the qualified VMU store. The first-socket screens A1/B1/C1/D1 map to
their proper Maple ports, while the SDK also supports second sockets A2..D2.
Original LCD readiness and orientation code consumes real native-owned virtual
device descriptions. No VMU is reported before the store/LCD owner is set up.
The original game's vmu_init probes these endpoints rather than fake callbacks.

A write copies all 192 input bytes into the endpoint's pending command. The
source may disappear when the original game returns from vmu_write. A second
write is busy until the original frame_vsync services that command and commits
the actual LCD buffer. Removal clears displayed pixels and discards the pending
packet before reattachment, so the tested removal sequence cannot show a prior
card's image. Pending commands must be drained before LCD shutdown. Calls stay
on the actual card owner's thread. LCD writes never modify VMU image files.

The hardware boundary supplies only the Kaede device-description/LCD-write
operations required here. Unsupported block commands fail. The original VMU
function bits identify its type; optional timer operations are not advertised
in its timer descriptor and have no implementation here. This is not a full
Maple driver, physical-controller driver, VMU firmware or VMU CPU emulator.
Future input/Maple work must extend this shared owner, not define duplicate
kdGetDeviceInfo/kdSetBlockWrite implementations.

Packing semantics preserved
The original game's packer lights any nonzero pixel byte. The SDK's assembly
blitters light only bit 3. Both rules are preserved. All four flip directions
and the default flag path match complete original Japanese instructions plus
an independent pixel/bit oracle. The game rotates its LCD image half a turn for
the original flipped-connector direction; readiness and orientation follow the
original SDK's actual descriptor interpretation and 16-entry orientation table.

Remaining scope
vmu_init now resolves in the actual native frame DLL. Six parent-startup symbols
remain absent: cable_mode, dat_8c78b4d8, dat_8c78b4dc, sbInitSystem,
sound_system_init and syCblCheckCable. This export frontier is not a count of
all dependencies still required for complete gameplay. vmu_frame_update's
whole game/player/Chao/puzzle state machine is not linked by this init slice.

The original main initializes VMU screens before card_init. A genuine native
startup coordinator must configure/open local card media and initialize the
LCD owner before that probe, then retain the actual original initialization
order. Setup does not silently create or format user cards. Drain/shut down
LCD service before its store owner; complete parent lifecycle integration is
still required. Close/reopen notifications that are not serviced between the
two actions need stronger per-card generation/handoff tracking before widget
support. Whole Chao/save transfers still require checkpoints and recovery.

The built-in Chao VMU execution core, original garden export/raise/import and
desktop widget remain required planned work in JP_VMU_EMULATOR_PLAN.txt. This
display of a Chao picture does not execute that VMU program or raise a Chao.
See JP_NATIVE_CARD_LIFECYCLE.txt and JP_NATIVE_VMU_FILESYSTEM.txt for preserved
card/transaction scope and original SDK limitations.
