The original operation
Handler64a828 checks admission, device readiness, cached root and capability.
It calls a name query for the first directory entry of type0xCC. Success from
that query returns zero, which makes the parent reject the operation with-245;
a missing-entry error is nonzero and allows the remaining checks. This original
gate is preserved exactly. The legacy export filename containing volume was a
provisional label; the verified predicate is specifically directory type0xCC.

The original FAT validator accepts FFFC/FFFF/FFFA markers and checks other links
against the user-area split and root limit. Relocation finds the lowest allocated
user block and the highest free FFFC block above it. It reads512 bytes into the
caller-provided workspace and completes the destination write before changing
metadata. A positive predecessor index updates its FAT link; otherwise the SDK
updates a directory-head field. The destination receives the source's old FAT
link, the source becomes FFFC, and the search repeats. The independent task plan
checks moves20->31 and21->30, exact data, directory head31 and FAT chain31->30.
No extra chain repair, validation or alternative allocation rule is invented.

When movement finishes, the original code sets all256 directory-dirty bytes to1,
then persists directory sectors and FAT. With the two-sector fixture the first
two dirty bytes clear after their successful writes; the other254 remain1.
Initial progress/error counters are preserved and incremented by actual block
attempts. The routine does not reset them to the delete/rename starting values.
