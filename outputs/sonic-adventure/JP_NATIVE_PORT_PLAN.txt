1. Establish the complete GCC baseline.

The original 247-image matching build was independently verified. The isolated
GCC workflow checks those original/rebuilt image hashes before and after make,
copies private inputs into a fresh worktree, and runs one make -j8 gcc there.
The first workflow stopped before making a worktree because of a mistyped hash
literal. Windows and WSL agreed on the intact input; v2 corrects that literal.
Keep both workflow files and logs. Use the terminal result and separate manifest
qualification report to determine whether the GCC build actually completed.
A running process, partial manifest or compile log alone proves no completion.
The GCC target is little-endian 32-bit SH-4, not x86/ARM. Even a passing GCC build
does not prove console runtime, native PC operation or full-game 60 FPS support.

2. Integrate coherent native platform dependencies.

An unchanged upstream task/heap source and our authored test bridge compile to
native Windows x64 objects with no diagnostics after a host size_t adapter.
The adapter uses the compiler's pointer-sized size_t through the SDK's existing
SIZE_T_DEFINED guard; it leaves Uint32 and upstream source bytes unchanged.
The initial build failed on that type conflict. The second reaches the linker
and stops on eleven imports. No third linking attempt or dummy implementation
was used; there is no linked DLL or heap/task runtime test from these probes.

See analysis/jp_native_link_dependency_inventory.json for the original providers.
The imports are collision_free, event_free, _unit_matrix_, njPushMatrix,
njPopMatrix, njTranslateV, njRotateX/Y/Z, njCalcVector and njAddVector. These are
whole-translation-unit imports; the heap functions themselves do not all call
Ninja. Some providers use SH-4 inline assembly in .c files, hidden under
__clang__ guards. A C filename or successful parsing is not a portable body.

Port real shared math/matrix and task/collision/event lifecycle providers as a
dependency group. Reuse verified USA numerical implementations where semantics
and calling conventions are established. Use the upstream GCC renderer's C
replacement and relocation metadata; direct hardware/store-queue paths still
need host interfaces. Defining GCC alone enables SH-4-specific headers and is
not a native-port configuration.

Make 32-bit disc addresses/data layouts explicit and separate them from host
pointers. Audit pointer-to-Uint32 casts, packed records, enum/long sizes and
relocated overlay imports. Do not widen every game scalar or cast raw disc
records to 64-bit host structures. Retain the upstream behavior guards needed
for modern compilers and verify floating-point operation order where relevant.

3. Bring up the native game loop and content path.

Create genuine host interfaces for input, time, files, memory, rendering, audio
and saves. Compile game and overlay code from source; retail modules supply
declared data, not executable SH-4 code for a PC build. Resolve shared symbols
and per-image ownership through the existing placement/import metadata.
First prove boot/menu, then a controllable stage with rendering/audio/save-load,
then all characters, stages, events, bosses, minigames and Chao. Keep the old
prepared-frame renderer proof as scoped reference evidence, not a game proof.
The old research rasterizer rejects real stage commands including offset colour,
VQ textures, filtering and fog; do not bypass those guards to claim completion.

The directory inventory contains 2,106 JP files and 2,832 USA files, with 1,748
common paths. Its 326 localization filename candidates are a heuristic list,
not 326 verified localized assets. The USA disc has EVENT_ADX_US.AFS alongside
EVENT_ADX.AFS. All extracted audio remains private.

The actual archives contain 2,088 JP Japanese clips, 2,044 USA Japanese clips

not an exact archive count. Independent payload comparisons identify 1,664

Resolve duplicate/unmatched clips through event/source context. Stage message

text/timing data and fonts/UI alongside the source, with verified USA mappings.
No English localization has been implemented by these inventories.

4a. Integrate actual VMU emulation and Chao round trips.

The user added a built-in VMU emulator and an optional desktop LCD widget.
Build on the real backup-file/card-storage work now underway. Once native

then test widget-to-game handoff and restart/crash recovery. Keep required retail

This is planned scope, not an implemented or working emulator. Existing VMU LCD
drawing, native save records or a simulated Chao-stat screen do not prove it.

5. Complete presentation features and later platforms.

After end-to-end native behavior is established, separate game logic timing from
60/120/240 FPS presentation. Upstream's 60 FPS implementation has documented
mode limits and draw-side-effect caveats; it is not proof of generalized high
FPS. Add up-to-8K rendering, aspect ratios and resolution controls. Then optional
SUPIR texture packs, HD toggle and 100/75/50/25/Off texture settings; Off samples
no textures and uses vertex/material colours. Keep original assets supported.

Carry the verified portable core to Android and stereoscopic 3DS, with measured
device-specific settings. Keep N64 and original PlayStation demakes as later
content/engine adaptations. Preserve the complete requested scope throughout.

For a beginner: consult the passing verification reports and each terminal
result. A compile-only probe, proposed mapping or queued job is explicitly not a
playable game. Keep Sol High for this integration work; Luna Low is suitable for
routine documentation and publication after a snapshot has been reviewed.
