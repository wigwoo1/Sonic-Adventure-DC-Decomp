Genuine texture initialization and game-owned record storage

Overall estimate: about 10% of the whole project, weighted milestones.
Goal active. Japanese matching/GCC baselines are verified. Full native gameplay,
English, enhancements and later platforms remain unfinished. No playable EXE.

What changed

The complete original njInitTexture body now runs in the actual shared frame
owner, calling the existing real njInitTexMemList. Two native entry/exit guards
prepare ownership and close its initialization window. Its original field
writes remain intact. The game can supply its native-width record table,
including main's 2,048 entries, rather than silently receiving another table.

The authored replacement owner includes the prior move/upload/retention owner
and adds caller-owned table lifetime. Caller tables are never freed by shutdown.
Owned tables can reinitialize/shrink in place and retain their actual allocation
capacity. Valid zero-record initialization is supported, including NULL/zero.
Allocation from an empty table is safely rejected by the existing native guards.

New sidecars allocate before replacement. Invalid alignment, partial overlap,
overflow/owned-capacity violations or insufficient budget leave caller storage,
the prior owner, path and error-surface metadata intact. Native initialization
retires old handles/payloads; submitted frame payloads remain retained until
their actual final reference retires. IDs never recycle. This native resource
cleanup is an explicit policy beyond the original initializer's memory writes;
the original caller must normally release old textures before initialization.

The original texture path, error-surface fields, record counter/cursor and
untouched list/cache/error values retain their actual behavior. Only path byte
zero is cleared. Virtual/physical error-surface pointers, record dummy fields
and native padding stay untouched. Persistent raw Ninja values are distinct
from native ownership handles; stale handles still fail lookup safely.

jp_texture_sdk_limits selects binding count and logical byte budget for SDK
initialization. Defaults are 16,384 bindings and 64 MiB. The entire logical
record table is charged even when caller-owned, with transient replacement
accounting. A shrunken heap table is still charged at its retained physical
capacity; a focused lower-bound/budget test covers this case. Frames retain
their separate existing budget. The prior explicit
jp_textures_initialize API keeps its original behavior and qualification.
One game thread owns these globals; caller storage must remain valid/writable.

external source 25a3d3154dbe657325e97dbe8c5291086f6af5c0. Retail JP binary and
local logo/title archives are needed for game-dependent tests. Use fresh output
folders; do not overwrite preserved proofs. Set PY/CLANG to local executables.
