Observed behavior
The sender requires a nonzero library root and nonzero object value. It does
not dereference the object parameter. It writes command 86 at 8c890628 and copies
four packet bytes sequentially to offsets 6,7,8,9. It invokes the actual SDK,
which constructs a real 20-byte queue entry, sets its ready word, advances the
tail and increments the count after copying. The original instruction order
matters for source/header aliases, overlapping queue buffers and partial faults.
Root-disabled error is d000001; null-object error is 07000103. Queue-full error
is the actual SDK a000001, with original diagnostics and mask restoration.

The existing handoff writes a raw pointer value to 8c88f7c8 and size&fffff800 to
8c88f7cc, rounding down to a multiple of 2048. It clears SR.T, preserves the
other status bits and does not allocate memory or validate the stored pointer.

forward aliases, SDK pipelined-copy overlap, count==256 rejection, above-limit/

Full CPU, RAM, FPU, banked/special registers, devices, Sound, runtime, flash and
ordered boundaries compare against original instructions. No packet data,
helper result, ARM acknowledgement, completed queue or checkpoint is injected.

All 1,987 earlier comparisons execute freshly in this DLL: 711 runtime/request/

A regression caught a Python fixture-name collision: the new buffer-helper name
hid the older packet-buffer constant BUFFER. The helper is now named HANDOFF;
the old constant remains 8cd42000. The native DLL did not change for this fix.
All affected tests were rerun with matching hashes. The superseded cold diagnostic
was explicitly stopped, preserved privately and excluded from qualification;
the replacement capture uses the corrected harness. The workflow checks inherited
integer constants as well as native APIs to prevent this kind of regression.

The first two retained command83 entries differ between profiles at payload byte5:
