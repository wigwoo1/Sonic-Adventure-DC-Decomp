Native frame waits and serialized vertical callbacks
===================================================

Status: VERIFIED component milestone. Estimated whole-project completion stays
about 10% of weighted milestones, not code coverage. Goal active. Japanese
matching/GCC source baselines remain verified. Native gameplay, English and
later platforms remain unfinished; these builds are not playable.

The complete original frame-pacing source now compiles natively. Its GCC game
behavior is selected locally in generated source, while SDK hardware headers
keep their existing Windows-compatible declarations. No fake SH-4 target macro,
interrupt-mask implementation or assembly stub is supplied. Original source
and matching proofs remain unchanged. The adapted complete presentation object
also compiles, with present_hold's spin replaced by the native wait service.

The three waiting paths are frame_wait, frame_wait_step and present_hold.
Callbacks run synchronously on the creating game thread. A rational logical
clock defaults to 60000/1001 Hz, independent of monitor refresh and timer 1.
It uses the existing 781250-count wall domain, carrying fractional deadlines
with integer arithmetic and rounding each deadline upward. It does not drift
by repeatedly using a rounded 13034-count period. Handler installation anchors
a fresh phase so a pacing reset after loading gets no retroactive callbacks.

Each pump bounds its callback batch and retains overdue work. frame_wait and
frame_wait_step synchronize overdue ticks before evaluating original pacing
state. This matters for frame_wait's late-count snapshot: a long draw must
produce the original negative countdown, not an apparently on-time frame.
Synchronization drains the backlog with host message checks between batches;
very long stalls can require many callbacks. Intentional pause/loading policy
must explicitly reset/reanchor instead of pretending those ticks never existed.

The Windows host adapter uses a real message wait and the verified native
window's pump. It preserves WM_QUIT for the application and recognizes a closed
window. Clock/host failure, missing callback and close are explicit errors.
The adapted frame functions return before further render/pad work on failure,
including a failure inside the held-picture wait. The application must check
jp_wait_status and stop its game iteration. There is no full application loop
yet. Invalid arguments/foreign-thread/reentrant calls are rejected. A callback
may inspect status/snapshot, but must not reenter/mutate the wait service.

frame_countdown remains a 32-bit int in the native source/header ABI. Callbacks
are serialized with the game, so there is no interrupt writer; wait predicates
use volatile reads. The game branches retain split-frame, interval-zero, stage
fog, sound, backup and loader ordering. No background timer calls into these
mutable game services. This is a native scheduling boundary, not an emulation
of the console's interrupt controller, physical scanout or interrupt FP state.
