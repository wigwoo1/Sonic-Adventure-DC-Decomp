Original container layer

buMakeBackupFileImage, buCalcBackupFileSize, buAnalyzeBackupFileImage and buCalcCRC.

Authored jp_native_backup_image.c adds byte-span/size/alias guards, prevents the

initial physical-card owner below supports the game's standard 128KB target.

Real native media owner
jp_native_vmu_store.c creates/opens eight separate 128KB card images, two slots
per controller port, VMU_A1.VMU through VMU_D2.VMU. Each holds 256 512-byte blocks.
Creation is explicit, starts unformatted and never replaces an existing card.
Open validates exact size; no missing-card or successful-write result is invented.
The owner uses native Windows headers, not the Dreamcast SDK's partial CRT
headers. Its compile recipe deliberately isolates those include paths.
The existing SONICADV_JP.SAV format is separate and remains untouched.

The owner retains an exclusive .lock sidecar while a card is attached. Cooperating
game/widget processes must follow this protocol; closing releases authority for
the next owner. A block write stages the complete image, flushes a fresh temporary,
then atomically replaces the prior image before committing the in-memory view.
Failed replacement leaves the previous disk/cache bytes intact and cleans its
temporary. Pre-existing external image edits are detected before replacement;
this does not prevent rename races from uncooperative third-party applications.
This is atomic block persistence, not an atomic multi-block filesystem/Chao transfer.
Whole-transfer checkpoints/backups remain required by JP_VMU_EMULATOR_PLAN.txt.
One creating thread owns operations. Errors are sticky until clear_error;
snapshot/close/shutdown remain available for inspection and cleanup. Future SDK
bridges must map captured errors per drive and handle retries explicitly.

71 actual filesystem assertions pass: all eight cards, block 0/17/255, all file
