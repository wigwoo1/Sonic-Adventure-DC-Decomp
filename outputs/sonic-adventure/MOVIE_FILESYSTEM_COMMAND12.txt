The recovered path
Command12 uses the original argument/opcode APIs and worker scheduler. It checks
free capacity, allowing the old file's block count, then opens a replacement
write handle. Normal writes create type33 directory records. Bit80000000 selects
an alternate path that writes, closes, reopens, reads each512-byte block and
compares all512 bytes. A mismatch returns-240; an original read error propagates.
Writing zero blocks creates an empty record; verification of that empty record
fails original read-open with-191 because its head isFFFF. These original rules
are retained, including their surprising results.

Write-open removes an existing record in RAM before allocating a handle. A full
handle pool can therefore return-249 after removing the cached old entry and
freeing its chain, with no persistence yet submitted. The recovery adds no
rollback. Next-block allocation searches downward for a freeFFFC block. A block
that is already a live directory head is reservedFFFA and the search repeats.
A failed data block is markedFFFF and the original writer retries other free
blocks; the first immediate-255 error is treated differently from errors inside
the retry loop. All corresponding tested control flow remains unchanged.

Close serializes the handle's type(CC when mode equals1,otherwise33), byte flag,
head, exact12 name bytes, eight encoded timestamp bytes, block count and signed
low16 attribute through the SDK-selected endian writer. Even bytes after a name
NUL are copied because close copies the full12-byte field. It marks the directory
sector dirty, writes directory metadata, then writes FAT metadata after directory
success. A nonzero reset argument initializes progress using the original
673bb4 slot table; zero retains the existing counters. All72 handle bytes clear.
The original opcode4 directly invokes this close path in a real worker task.

Original error guarantees
Close propagates a negative directory-write result and ignores the final FAT
persistence result. The command12 master ignores close's return. Consequently,
command12 can report success after a directory failure; standalone opcode4 can
report a directory failure; both can ignore a final FAT error. Metadata relocation
inside the directory writer can also cause a second FAT pass from close.
Tests preserve these exact distinctions. A success callback or ACK ledger is
not a guarantee of physical flash durability, atomic saves or power-loss safety.
